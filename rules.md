# Inlo — Antigravity Project Rules

These rules are binding project constraints. Apply them to every task unless the founder explicitly approves a documented change.

## 1. Source-of-truth order

When instructions conflict, follow this order:
1. User’s latest explicit decision and approved business/legal constraints.
2. `prd.md` for product scope and acceptance criteria.
3. `architecture.md` for system boundaries and security/transactional design.
4. `design.md` for visual language and UX quality.
5. `phases.md` for current delivery phase and release gate.
6. `memory.md` for durable decisions and current known status.
7. Existing code conventions that do not conflict with the above.

Do not silently resolve a material conflict by guessing. Stop the affected scope, explain the conflicting assumptions, and propose a reversible option. Never silently change the product from multi-activity access to a single-category gym app, or vice versa.

## 2. Work style

- Inspect repository structure, `package.json`, framework version, environment patterns, and existing components before editing.
- Build a small vertical slice with complete behaviour, tests and UI states; do not scaffold every route with fake content at once.
- Preserve existing working functionality and unrelated changes. Never wipe files, reinitialise the repository or replace the package manager without explicit need.
- Keep changes small enough to review. Prefer clear, domain-named functions over speculative abstractions.
- Do not invent product requirements, venue data, testimonials, prices, legal terms, partner commitments or policy defaults.
- If an unresolved business/legal decision blocks real-money behaviour, implement a disabled/configurable interface or test-mode flow and report the blocker. Do not invent a default policy.
- Do not report a feature as done unless it exists, is wired to real behaviour, and its documented checks were run.
- Keep a short progress summary in the current task and update `memory.md` only with durable project facts.

## 3. Technology rules

- TypeScript strict mode; avoid `any`. If an unavoidable boundary needs a type escape, isolate it and comment why.
- Follow existing package manager and lockfile. Do not install overlapping component, state, date, form or animation libraries without demonstrating a need.
- Use Next.js App Router patterns consistent with the installed version. Do not mix Pages Router conventions into App Router routes by accident.
- Keep database writes and privileged operations on trusted server paths.
- Use managed PostgreSQL as the transactional source of truth. Do not add microservices, Redis locks, Kafka, Kubernetes or a dedicated search cluster to an MVP task without evidence and explicit architecture review.
- Schema changes must be migrations committed to version control. Do not hand-edit production database structure as a normal workflow.
- External integrations need an interface boundary so provider-specific code can be tested/replaced.

## 4. Security and authorisation — no exceptions

- Never expose DB service-role keys, payment secrets, webhook secrets, signing keys or private provider credentials to the browser. A `NEXT_PUBLIC_` variable is public.
- Never commit `.env`, live credentials, private certificates, OTPs, real identity documents, access tokens or production personal data.
- Validate every untrusted request server-side, including IDs, pagination, prices, timestamps, state transitions and strings.
- Enforce role and ownership checks on the server and through RLS/DB policy where available. Hiding a button or route link is not authorisation.
- Partner access is scoped to explicit partner membership and assigned venues. Admin privileges must not be derived from user-editable profile fields.
- Apply rate limiting or document why it is not required for auth, OTP, booking, cancellation, check-in, payment/order and sensitive admin endpoints.
- Never log credentials, OTP, raw payment details, full sensitive webhook payloads, private documents or unnecessary personal data.
- Verify payment webhooks using the provider’s current documented signature algorithm and the required raw request body. Reject invalid signatures.
- Store only the minimum personal/KYC data needed for an approved workflow; use private storage and controlled access for sensitive files.
- No legal/privacy compliance claims should be generated by code comments alone. Record pending obligations and require counsel/owner approval where appropriate.

## 5. Money, credit and booking invariants

- Credits are integer entitlements, never floating-point values. Money is paise/integer minor units or a deliberately chosen exact numeric type; never IEEE floating point.
- The database ledger is the audit source for credit movement. Every grant, consumption, refund, expiry, reversal or admin adjustment needs a ledger entry and reference.
- Never edit/delete posted ledger history to “fix” a balance; add a compensating entry with reason and actor.
- Never trust price, credit cost, balance, eligibility, payment status, capacity or refund amount sent by the client.
- Booking capacity decrement, booking record, credit debit/allocation and booking event must succeed or fail atomically.
- Use an idempotency key for booking/payment operations. A retry must never double-book, double-debit or issue duplicate credits.
- Payment redirects are not proof of payment. Verified provider response/webhook plus database idempotency drives the entitlement grant.
- Store provider event IDs and external references; reconcile duplicates and out-of-order events safely.
- Cancellation/refund/no-show/venue-cancelled treatment must come from an approved, versioned policy. Do not hardcode a percentage or deadline before it is agreed.
- Keep money accounting, credits and partner settlement as related but distinct domains.
- Do not enable live partner payouts without approved merchant/marketplace structure, provider support, required due diligence and reconciliation.
- If money/credit/booking state becomes ambiguous, preserve the record and flag it for reconciliation. Do not “guess successful”.

## 5A. Entry/exit metering — additional non-negotiable invariants

- A scan is an event, not a price. Pricing policy is versioned, server-owned and accepted by the member before a metered visit begins.
- Fixed-price sessions remain the default unless a documented pilot decision enables metering for a specific category/venue.
- Before entry, the member must see rate unit, rounding/minimum rule, estimate and hard maximum debit. Never implement uncapped or surprising post-visit debits.
- The server timestamp is authoritative. Ignore client-submitted duration, price, rate, cap or client clock for financial calculations.
- Entry and exit requests are idempotent; one visit can have one valid start and one valid completion. Replays, duplicate exits, wrong-venue scans and invalid state transitions must not create ledger effects.
- Missing exit stops at the disclosed cap and creates an operations exception. Do not continue billing in the background. Any adjustment must be reasoned, audited, policy-compliant and explicitly communicated.
- Session completion, final debit, ledger entry and booking/session state update must be atomic. Store the exact rate-card/policy version and enough inputs to reproduce the calculation.
- Static venue QR alone is not proof of member identity or physical presence. Use a scoped token and appropriate staff/booking binding; do not overclaim GPS accuracy.
- Online validation is MVP default. Do not queue unverified offline scans in local storage and later treat device timestamps as authoritative.
- Never edit historical ledger entries. Corrections use compensating entries and an audited adjustment workflow.

## 6. Database and state management

- Use foreign keys, unique constraints, check constraints and transactions to enforce critical invariants, not only UI checks.
- Use a unique key for webhook event IDs and operation idempotency in the correct scope.
- Use DB row locks or equivalent atomic conditional operations for last-slot capacity races; a cache lock alone is insufficient.
- Every state machine transition is validated in one server-side domain function and recorded with actor, timestamp and reason.
- Use UTC internally and display venue-local time. Be careful around date boundaries and daylight/timezone assumptions.
- Make scheduled tasks idempotent and add reconciliation for tasks that could be missed.
- No direct browser writes to privileged booking, payment, ledger, settlement, role or audit tables.

## 7. UI/UX and anti-slop rules

- Read `design.md` before changing any visual component or page.
- Use design tokens for colour, spacing, radius, typography and semantic statuses. No ad hoc palette per page.
- Build Inlo as a human, editorial, activity-led marketplace—not a generic AI SaaS template.
- No arbitrary gradients, glassmorphism, glowing card borders, random floating 3D blobs, emoji core icons, endless marquees or gratuitous scroll effects.
- Avoid fake ratings, fake reviews, fake scarcity, invented logos, placeholder venue imagery presented as real, fabricated metrics and fake booking success.
- Use one consistent icon set and component geometry. Do not hand-roll a new button/card for every route when a shared component can work.
- Primary action must be obvious and accurate. Keep price, credit cost, relevant rules and booking outcome clear before commitment.
- Implement loading, empty, disabled, error, selected and success states. Do not leave inert controls or buttons that merely look functional.
- Mobile-first at 360px minimum review width; also test tablet and desktop. No accidental horizontal overflow.
- Provide labels, keyboard navigation, focus-visible indication, meaningful alt text, sufficient contrast and reduced-motion support.
- Do not use animation to delay critical booking or payment interactions.
- Prefer authentic, approved venue imagery. If unavailable, use a designed placeholder clearly treated as a placeholder.
- Use real content and specific microcopy; avoid “Lorem ipsum”, “Unlock your potential”, vague “Learn more” labels where a precise action fits.

## 8. API and error handling

- Return structured, safe error responses with stable codes; never leak SQL statements, stack traces, environment values or provider secrets.
- Use appropriate HTTP status codes and avoid treating every failure as 200/success.
- Preserve request context/correlation IDs for investigating failures without storing sensitive values.
- Apply timeouts and bounded retry policies for external services. Do not retry non-idempotent operations blindly.
- User-facing errors must tell the person what they can do next when possible.
- If a third-party provider is unavailable, show a truthful pending/failure state and a support/retry path.

## 9. Testing and definition of done

For every feature, add tests at the appropriate levels. “It compiles” is not done.

Minimum quality checks for a relevant task:
- Lint and type-check pass.
- Unit tests for calculations and state transitions.
- Integration tests for DB invariants, ownership/RLS and critical transactions.
- Playwright/browser flow for critical user journeys and responsive states.
- `npm run build` (or the repo’s equivalent) succeeds.
- Real browser inspection for any UI change at mobile and desktop widths.
- Error/loading/empty/success states checked.
- No secrets or private data leaked to client bundle/logs.
- Migration and rollback/recovery implications considered.
- Final summary states exact commands run and any tests not run; never imply missing tests passed.

Critical mandatory test cases:
1. Two concurrent requests compete for the final slot; at most one confirms.
2. Duplicate booking request with same idempotency key has one effect.
3. Insufficient eligible credits leaves no partial booking/capacity change.
4. Duplicate payment webhook grants entitlement once.
5. Invalid webhook signature cannot alter payments/credits.
6. Provider success redirect with no verified payment grants zero credits.
7. User/partner cannot access another user/partner’s private resource.
8. Invalid booking status transition is denied.
9. Cancel/refund logic follows versioned policy and keeps ledger consistent.
10. Stale availability results cannot force an oversold booking.

## 10. Scope discipline and dependencies

- Follow the current active phase from `phases.md`. Do not sneak in phase 5 payments during a phase 2 catalogue task.
- No live payments/payouts before legal/finance gate approval.
- No native apps, AI recommendation system, dynamic ML pricing, or multi-city rollout without a product decision.
- Avoid dependency sprawl. Before adding a library, check maintenance, license, bundle size, accessibility, compatibility and whether existing stack already solves the need.
- Do not copy-paste an entire UI component registry just because it is visually impressive. Adapt only components used in a specific product requirement.
- Keep secrets and local setup instructions in `.env.example` using dummy placeholders only. Never include `.env.local`, real credentials, build caches or generated TypeScript build info in handoff ZIPs. If a shared archive contains `.env.local`, inspect values privately and rotate any non-placeholder credential before sharing the repository further.

## 11. Antigravity response format for completed tasks

At the end of a meaningful coding task, report:
1. **Implemented:** exact user-visible and backend behaviour.
2. **Files changed:** key files and migrations.
3. **Validation run:** commands, test outcomes and browser/device checks actually performed.
4. **Security/data notes:** permissions, secrets, provider events and migration concerns.
5. **Open issues:** blockers, skipped checks or decisions requiring founder input.
6. **Memory update:** durable decisions/status recorded in `memory.md`.

Do not produce a long generic explanation in place of shipping and validating the requested code.
